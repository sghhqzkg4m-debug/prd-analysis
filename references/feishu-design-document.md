# 飞书设计文档收敛规则

飞书设计文档面向设计评审，不是产品、架构、接口和前端实现规格的合集。目标是让评审者快速判断：为什么做、为谁做、任务如何完成、页面怎样组织、状态与风险如何反馈、设计是否可验收。

## 业务／产品目标、设计目标与讲解顺序

- 推荐讲解顺序为“业务问题、业务目标与版本定位 → 用户、JOB、Case 与目标体验／设计目标 → 竞品参考与设计取舍（有研究价值时）→ 本期方案与页面交互 → 待决策 → 验证”。固定叙事原则，不固定章节数量、编号或名称；简单任务允许合并。各维度是否显示按 [feishu-analysis-framework.md](feishu-analysis-framework.md) 判断。
- 开篇只用短段落说明业务问题、业务目标与规划确定的版本定位，并标注规划来源。规划缺失或冲突时写明待确认，不由设计分析代替规划定性；有主次目标时沿用规划结论。Case 中将用户完成任务时应获得的体验改善融入关联的业务／产品目标，使业务结果与用户体验相互支撑，不另列体验目标。不默认输出目标大表、范围表、完成标准或待确认清单，也不在摘要和首章重复同一组结论。
- 完成标识放入对应 Case 与验收；凭证安全、权限和高影响操作要求放入对应页面。收益基线与测量限制放入验证说明，不在开篇堆叠防御性声明。
- 待决策集中放在方案之后，读者理解方案后再讨论问题。影响当前页面解读的假设必须在对应任务、页面或规则处就地简短标注，可引用待决策编号；不得为流畅叙事把未确认规则写成事实，也不在开篇铺开编号。
- 按“业务／产品目标（融入体验诉求）→ 设计重点 → 设计目标”推导。先在分析时辨明业务结果与该 Case 的角色在具体场景中希望获得的体验变化，再合写为一条完整的业务／产品目标，不用两个标签或两段话并列呈现，也不含设计手段。体验表述要说明它如何支撑业务结果，不能只在句末附加“体验良好”。设计目标由综合目标推导，通常用一两句话写清场景、角色、关键设计手段和预期体验改善；手段写信息组织、预检查、反馈或交接等机制，不写固定控件或未经确认的能力。详细策略留在方案，完成标识留在 Case，观察标准和验证方法放在验收；业务指标不直接充当设计目标。
- 每个 Case 单独写设计目标。通用组织方式是“在[场景]，通过[关键设计手段]，让[角色]获得[体验改善]”。可按任务特点调整语序与重心：**前后变化式**表达有证据的现状阻碍如何借助手段转向目标体验，仅在现状有证据时使用；**关键决策式**表达手段如何帮助角色理解关键判断及后果；**协作交接式**表达手段如何让相关角色以更清楚的边界或更轻的负担完成交接。三种写法是选择依据而非必填模板，不与场景类型机械绑定；目标句只保留最关键的机制与体验改善，具体操作和“能否”检查移到方案与验收。
- 每个 Case 的设计目标都要同时回应综合目标中的业务结果与体验诉求；两者无法形成有意义的关系时，检查目标、Case 范围或证据，不硬凑手段。HTML 中按“业务／产品目标 → 设计重点 → 设计目标”纵向呈现，飞书文档也保持同样的推导关系。Case 完成标识留在任务说明，验证方法留在验收章节，不为目标额外生成独立的“观察标准”卡片。创建对象、拿到配置、真实接入成功和持续可用是不同阶段，不能互相替代；原型模拟也不能证明真实业务完成。
- 能够基于可靠基线和一致统计口径量化时，为 Case 补充指标、目标值、测量方式与周期；暂不可量化时使用可观察的行为与结果标准，不用主观数字替代证据。
- 写完目标后做一次反向检验：业务／产品目标若只是在列举“建设入口、支持策略、提供密钥”等能力，应改写为目标对象实际发生的业务变化；若只写“简单、清晰、能完成”，应补足业务结果与 Case 中希望改善的体验品质，但不塞入方案。设计目标若只重复综合目标而没有关键手段，就不能指导取舍；手段若变成多个按钮、字段或步骤的罗列，应上提到机制层并把细节移到方案；“能判断 A、能解释 B、能修正 C”这类任务检查清单移到验收。关联使用语义名称或 Case 上下文，不为目标自造字母编号；无法连通时标记证据缺口，不伪造用户问题或收益。
- 角色覆盖关键交接双方；岗位归属不明时标待确认，不预设客户组织。平台能力应映射到结果导向的 Job，而非直接用算法名作 Job。
- 不编造效率、成本、成功率收益或客户情绪。定量目标需要基线与证据，缺少时用任务观察验证。
- 明确区分用户要求、设计建议和待确认约束，尤其是最小数量、禁用组合、权限和上线范围。

## JOB、Case 与场景阶段

- JOB 描述用户为达成业务结果所需的一组任务，采用“xxx（用户）需要在 xxx（场景）下，完成／进行 xxx（任务）”。避免用菜单、按钮或单一步骤替代 JOB。
- Case 描述 JOB 下由具体情境触发的任务场景，采用“在 xxx（场景）下，完成／进行 xxx（任务）”。为每个 Case 补充起点／前提和可观察的完成标识。
- 阶段是完成 Case 的步骤。不得把同一场景中的准备、配置、交接等连续步骤机械拆成多个 Case 或 JOB。不同触发条件、协作路径或完成结果才构成拆分依据；不固定 JOB、Case 或阶段数量。
- 异常作为对应 Case 的分支合并呈现，写清触发条件、用户可见反馈、可执行操作、恢复或退出路径及恢复后的完成标识，不另建异常 Case。首次路径只在相应 Case 中保留失败时的交接与返回，避免暗示所有成功任务都必经排障。
- “简单、安全、高性价比”等上层诉求可保留为背景，并映射到本功能的业务任务；不擅自把诉求全部纳入本期。

## 用户旅程的选择与展示

- 规划包含体验优化目标时，围绕受影响的 Case 加深现状体验分析：任务动作与判断、证据支持的断点、对用户和业务的影响、已证实成因与待验证假设、设计机会、改善目标和验证方法要能相互追踪；不要把“体验优化型”仅写成开篇标签。
- 当任务跨阶段、跨角色或跨触点，且有交接与体验断点时，使用用户旅程。单页短任务用任务流程即可。
- 飞书优先使用可编辑的现状—目标对照旅程白板。一个图围绕一个 Case，横向为业务阶段；跨角色协作时将主要执行角色分别成行，写清每阶段谁做什么。图前说明角色定义与 Case 的起点、完成结果。
- HTML 的现状旅程使用更完整的阅读结构，具体遵循 [html-current-journey.md](html-current-journey.md)。角色泳道只承载角色动作和交接关系；用户目标、触点与反馈、想法与疑问、现状断点、改进机会、责任、衡量与证据分别作为与阶段对齐的体验行，不把这些内容混进“主要执行者”单元格。
- 用少量原生箭头突出关键跨角色交接，说明交接物或结果反馈。任务角色可由同一人承担；岗位归属、责任人和审批环节缺少证据时标待确认，不自行增加审批。无阶段动作的角色不必占据整条泳道；系统自动动作仅在已知且影响任务理解时单独呈现。
- 角色动作下按需加入“交接／阶段结果、现状断点、目标体验、设计策略”。目标体验表达业务改善，设计策略表达支持手段；不把待验证方案称作已经验证的亮点。信息密度高时合并非关键维度，不机械填满每个格子。
- 每阶段每格保留一到两个主要信息点。旅程交代业务协作与恢复闭环；页面章节进一步说明入口、操作、分支、反馈和返回。异常路径必须并入对应 Case，不能因已有状态表而省略，也不能另建异常 Case。
- 标明现状证据、目标方案与未知环节；没有访谈或测量证据时不画情绪曲线、耗时和满意度分数。
- 不把采购、扩容或后续治理自动纳入本期；可作为背景或待确认场景。

## 章节合并与追踪

- JOB、Case、角色定义与对应旅程集中呈现，或拆成相邻的“JOB 与角色”和“Case 旅程”章节。已有角色表、核心任务表、任务闭环图中重复的动作与交接合入旅程，不重复保留一整套叙述。
- 本期范围放在整体方案开头，默认用“用户任务 / 本期设计覆盖”简表，非范围以短说明补充；少量内容可直接用段落。不默认增加“待确认边界”列，完整问题清单归入待决策。旅程不再承载完整范围清单。
- 保留“业务／产品目标（含体验诉求）→ 设计目标 → Case／阶段 → 设计策略 → 页面／验收”的必要追踪，并检查设计目标同时回应其中的业务结果和体验改善；短引用即可，不另建重复的大表。客户特征、落地障碍、版本分期与收益按触发条件融入现有章节，不另建固定的并列章节。
- 更新时先确认替代内容完整且可读，再移除被替代的章节／图表；核对编号、交叉引用、人工补充和原生组件是否保留。

## 内容重心参考

竞品研究的深度、证据和呈现统一遵循 [competitive-analysis-gate.md](competitive-analysis-gate.md)。正文按设计问题呈现关键比较与取舍，完整操作记录放附录；不为形式完整强制增加竞品章节，也不把竞品先例当成本产品体验已验证。

- 约 70%：用户任务、现状与目标体验、信息架构、流程、页面和交互。
- 约 20%：状态、权限、安全、异常反馈和恢复。
- 约 10%：直接影响交互的技术约束、证据缺口与待确认项。

比例用于控制重心，不要求机械统计字数。

## 主体应关注

1. 设计结论：问题、推荐方案、核心体验、范围。
2. 用户与场景：角色、触发条件、Job、完成标识。
3. AS-IS / TO-BE：体验断点与目标路径。
4. 范围与关键约束：本期、非范围、会改变页面的依赖。
5. 信息架构与入口：候选比较、选择和取舍。
6. 核心任务流程：主路径、分支、失败和恢复。
7. 页面与交互：信息优先级、结构、操作、反馈、线框。
8. 状态、权限与异常：可见性、可操作性、危险操作与恢复。
9. 关键文案：状态、校验、成功、失败和确认。
10. 设计验收与待确认：任务完成性、高风险状态和真正会改变设计的问题。

章节可根据复杂度合并，不要求固定数量。

## 下沉或压缩

以下内容仅在直接改变入口、字段、状态、权限、反馈或恢复时，以一两条约束或待确认项保留；否则移入 UI generation spec、技术规格或附录：

- 后端组件选型、部署位置、网络拓扑和配置权威。
- 路由、Hash、轮询、冷却、探测和限流的底层算法。
- 完整协议矩阵、接口字段、错误码和重试实现。
- P95/P99、吞吐、容量和分布式实现。
- 用户不可见、不可操作的完整技术对象模型。
- 全量需求追踪、接口追踪和测试数据。
- Workspace 路径、工具日志、授权过程和生成步骤。

## 仍需保留的技术约束

技术问题会直接改变用户体验时不能删除。例如：

- 流式响应开始后能否切换实例。
- 成员异常时聚合状态如何变化。
- 删除或停用影响哪些用户对象。
- 密钥是否只展示一次。
- 两类接入来源是否允许混选。
- 模型不一致时能否提交。
- 配置是立即生效还是需要发布。
- 并发编辑冲突如何处理。

文档描述用户可感知语义和设计处理，不代替研发给出底层实现。

## 与 UI generation spec 的边界

飞书设计文档回答：

- 用户为什么来、怎样完成任务。
- 页面展示什么、如何决策和恢复。
- 设计选择和可验收结果是什么。

UI generation spec 回答：

- AI 要生成哪些页面和载体。
- 组件树、字段、校验、状态矩阵和 Mock 是什么。
- 哪些文件或区域允许修改、实现顺序和验收方式是什么。
- 哪些精确组件/API 必须在 Workspace 中核查。

两份产物共享业务结论，但不互相复制全部内容。
