# HTML 现状用户旅程结构

用于 `html-delivery` 中按 Case 展示现状用户旅程。它规定内容结构和关系表达，不规定颜色、字体、圆角或装饰样式；视觉继续继承用户提供的模板或当前 HTML 的设计语言。

## 适用与边界

- 一个旅程围绕一个 Case，图前写明产品／模块、核心用户、其他目标用户、场景、覆盖范围、起止边界、地图性质／证据状态、参与角色和阅读规则。核心用户只表示该 Case 的主要体验主体，不表示其他角色不重要。
- 横轴使用两级结构：第一层是业务阶段分组，第二层是子阶段／动作步骤。真正与下方内容对齐的最小列是动作步骤，不是整个阶段；体验维度与参与角色纵向排列。阶段、子阶段和动作列数量均由实际任务决定。
- 同一阶段可跨多个动作列，同一子阶段也可有多个动作。为动作分配稳定编号（如 `A1`、`A2`），让所想、痛点、需求、点子和证据逐动作对齐，避免整阶段信息混成一段。
- 现状旅程描述用户当前如何完成任务。目标体验与设计建议作为“改进机会／责任”行呈现，不把未来方案混写成现状动作。
- 多类用户的目标或情绪显著不同时，分别绘制旅程；不要把多个人的目标、想法和情绪合并成一个“主要执行者”。
- 本文件中的方括号内容是生成模板提示。生成真实项目 HTML 时使用有依据的项目内容替换；没有适用内容时删除相应可选行，不把提示语留在最终交付中。

## 推荐阅读结构

按以下顺序纵向组织。每一行都与顶部业务阶段逐列对齐。

1. **旅程上下文**：产品／模块、核心用户、其他目标用户、场景、覆盖范围、起止边界、地图性质／证据状态、参与角色／阅读规则。
2. **阶段分组表头**：`[阶段编号与名称]` 跨越其包含的动作列，并补 `[阶段目标／关键结果]`。阶段宽度由所含动作列数量决定，不默认代表耗时。
3. **子阶段／动作列表头**：每个最小列填写 `[子阶段编号与名称]` 或 `[动作步骤名称]`，并补 `[触发／触点／用户可见反馈]`。没有子阶段时直接使用动作步骤；若需要表达耗时，单独标注有证据的持续时间。
4. **多角色协作泳道／用户所做**：核心用户一行，各协作角色分别一行。动作卡放入其所属的最小动作列；每张卡显示 `[动作编号] [动作／判断] [输入、输出或完成标识]`。确无动作使用 `—`。岗位归属不明时使用 `[角色待确认]`，不自行发明岗位或审批。
5. **所说所想／疑问**：每个动作列填写 `[A1 · 有证据的用户原话／疑问]`；若只有合理推断，明确写 `[A1 · 推断：待研究验证的问题或不确定性]`。不把设计团队的解释写成用户原话。
6. **情绪走势（可选）**：以动作列为采样点，仅在有研究或测量证据时绘制，并注明来源、尺度和样本；模板提示写 `[仅在有证据时绘制；否则删除本行]`。不得为了视觉完整编造曲线、耗时或满意度分值。
7. **现状断点／关键时刻**：每个动作列填写 `[A1 · 有证据的阻碍、负担或不确定性]`，必要时补 `[关键时刻及其影响]`。
8. **用户需求**：将痛点转译为用户希望获得的能力或结果，使用 `[A1 · 用户需要一种方式来……以便……]`；需求必须对应现状动作和痛点，不直接写成某个界面控件或既定方案。
9. **设计点子／优先级／责任**：按需求列出候选点子，写明 `[点子名称] [高／中／低或待评估] [对应需求／动作编号] [建议责任角色／待确认]`。点子是方案假设，不能混入现状动作，也不能把参考材料中的功能自动当成本期承诺。
10. **衡量与证据**：每个动作列按动作或需求填写 `[验证指标及口径]` 和 `[现有证据／待采证方式]`。没有可靠基线时不填写目标数字。

## 角色泳道与连接线

- 角色行只承载动作节点。动作节点使用跨行稳定的编号，同一阶段有多个动作时按先后顺序排布，不合并成长段文字。取消独立的“交接／结果”整行；交接物、接手条件和结果反馈直接标在线上，或紧邻交接点显示。
- 主流程沿动作列从左向右。换角色时使用水平加垂直的直角折线，转折位于动作列间隙或节点外侧；连接端点必须落到对应动作节点。
- 并行工作使用清楚的分叉和汇合。若后续动作要求多个输出齐备，在汇合处标 `[全部条件满足后进入下一步]`；若任一输出即可继续，标明实际条件。
- 异常与返工使用区别于主流程的虚线或其他非颜色单一编码，沿泳道外侧的专用通道返回，并标 `[触发条件 → 返回阶段／恢复动作]`。
- 只连接真实的前后依赖、交接和反馈，不为同列对齐或每个状态都画箭头。连接线不得穿过节点、文字或标签。
- 交接复杂时在图下补充短说明：`[交接编号] [发起角色 → 接收角色] [交付物] [接手条件] [失败时处理]`。说明用于解释连接关系，不重复整段角色动作。

## 空白模板文案

生成结构模板或无具体业务内容的示意 HTML 时，只使用以下类型的方括号提示，不填写案例：

```text
[产品 / 模块]
[核心用户 / 用户目标]
[其他目标用户]
[场景 / 起止边界]
[覆盖范围]
[地图性质 / 证据状态]
[参与角色 / 阅读规则]

[阶段编号与名称 / 阶段目标或关键结果]
[子阶段编号与名称；无子阶段时使用动作步骤名称]
[触发 / 页面、渠道、人员或系统触点 / 用户可见反馈]
[A1 · 核心用户动作 / 判断 / 输入 / 输出 / 完成标识]
[A2 · 协作角色动作 / 判断 / 输入 / 输出 / 完成标识]
[A1 · 有证据的用户原话 / 疑问；无证据时标推断或删除]
[仅在有证据时绘制情绪；否则删除本行]
[A1 · 有证据的阻碍、负担或不确定性]
[关键时刻及其影响]
[A1 · 用户需要一种方式来……以便……]
[点子名称 / 优先级或待评估 / 对应动作与需求]
[建议责任角色 / 待确认]
[验证指标及口径]
[现有证据 / 待采证方式]
```

不要写入具体产品名、角色名、业务动作或示例数据。不要把配色从其他示例 HTML 复制进当前模板。

## 响应式与可访问性

- 桌面端完整显示阶段矩阵；宽度不足时仅旅程容器横向滚动，正文页面不整体溢出。
- 旅程提供“全屏查看／退出”控件，全屏时保留阅读层筛选与旅程容器滚动；支持 Esc 退出。原生全屏不可用时可用铺满视口的阅读层降级，退出后恢复页面滚动。
- 阶段表头与左侧行名在滚动时可按现有视觉体系选择是否粘性定位；粘性元素不得遮挡连线或内容。
- 相邻阶段使用不同但协调的浅色底与强调色，阶段所含的子阶段／动作表头继承同一色系；阶段交界处同时使用较强竖向分隔线，让分组不只依赖颜色。色彩继承当前 HTML 的品牌体系，不照搬参考示例配色。
- 阶段数量超过现有色组时，可循环使用色组，但相邻阶段不得使用同一色组；不得把阶段色扩散到痛点、需求、点子等语义色，避免混淆阶段归属与内容类型。
- 保持可读字号，不通过整体缩放把宽图塞进窄屏。连接线使用 SVG 时随容器尺寸重绘，并提供文本化交接说明作为可访问补充。
- 使用标题、表格语义或等价的 ARIA 描述说明横轴为阶段、纵轴为体验维度与角色；颜色不能成为区分主流程、并行和异常的唯一方式。

## 阅读层显隐筛选

- HTML 旅程图在矩阵上方提供复选框，至少支持独立显示或隐藏：`所做`、`所说／所想`、`情绪曲线`、`痛点`、`需求`、`点子`。
- 筛选仅改变当前阅读视图，不删除、改写或重新计算旅程数据。切换后阶段和子阶段表头仍保留，剩余内容继续按原动作列对齐。
- 默认显示所有实际存在的内容层。真实项目因无证据而删除情绪等可选层时，对应筛选项也应自动隐藏或不生成，不能出现点击后无变化的空控件。
- 控件使用原生复选框或等价的可访问控件，具备清楚的组标签、键盘焦点和选中状态；不能只依赖图标或颜色表达显隐状态。
- 一个 HTML 中有多个 Case 时，每张旅程图使用各自的筛选组，仅控制本图内容，不影响其他 Case。

## 最小检查

- 横轴是否由“阶段分组 → 子阶段／动作步骤”组成，角色和体验维度是否纵向排列。
- 相邻阶段是否有可辨识的同系色分组，子阶段是否继承阶段色，阶段边界是否还有非颜色分隔线。
- 所说所想、情绪、痛点、需求、点子和证据是否与最小动作列对齐，而非仅按整阶段归并。
- 是否标明核心用户、其他目标用户、用户目标和覆盖范围；阶段下有真实子阶段时是否展示。
- 角色动作是否按角色拆行，而非只分“主要执行者／协作角色”。
- 同一阶段存在多个动作时，是否使用动作编号保持“所做—所想—痛点—需求—点子—证据”的追踪关系。
- 交接是否由有端点、有标签的连接线表达，而非独立“交接／结果”行。
- 并行、汇合、失败返回和完成条件是否可读，连线是否避开节点与文字。
- 事实、推断、目标方案和待确认是否清楚区分；无证据时是否删除情绪和数字。
- 用户需求是否表达期望能力或结果，设计点子是否作为带优先级与责任状态的方案假设单列。
- 所做、所说／所想、情绪、痛点、需求和点子的显隐筛选是否可独立操作，且不会破坏动作列对齐或改变源数据。
- 结构模板是否仅含方括号提示，且没有复制参考示例的具体内容或颜色。
