# 飞书组件路由

## 内容到组件

| 内容 | 首选组件 |
|---|---|
| 核心结论、设计主张 | 引用块或强调段落 |
| 多字段映射、方案比较、权限、状态 | 原生表格 |
| 多步骤、分支、回退、循环 | 原生白板流程图 |
| 导航或页面层级 | 原生白板结构树 |
| 对象归属和引用 | 原生白板关系图 |
| 业务／产品框架、资源拓扑与跨域映射 | 分区容器＋对象节点＋带标签连线的原生白板 |
| 已确认的信息布局 | 完整比例线框图图片 |
| 简短线性说明 | 段落或列表 |

同一信息不同时使用图、表和长文字重复表达。图需要回答明确的设计问题。

## 面向讲解对齐的组件组合

- 开篇可用少量原生引用/高亮块承载业务问题、业务目标和关键边界，每块一两句；Case 中将角色的体验诉求融入对应的业务／产品目标，再推导设计目标，不另列体验目标。颜色表达语义，不按段落轮换装饰色。
- 范围放在方案开头，用“用户任务 / 本期设计覆盖”原生简表；非范围短述，待决策后置，不默认添加待确认列。
- 入口与页面结构树回答在哪里、归属谁；页面流程图回答如何完成任务。包含关系与跳转关系分别表达。功能树与页面树高度重复时择一。
- 跨页面任务用简化页面框或缩略图加原生连线，标明操作、成功/失败、取消/返回以及系统边界。完整页面细节留在对应页面说明中。
- 用户旅程按 Case 组织：阶段为列，参与角色分行，用原生箭头标关键交接物和结果反馈；现状断点、目标体验与设计策略作为阶段对齐的独立信息层，不混入角色动作。未经访谈的问题标为推断。控制维度数量，目标体验和设计策略可合并。飞书规则见 [feishu-design-document.md](feishu-design-document.md)，HTML 现状旅程见 [html-current-journey.md](html-current-journey.md)。
- 竞品界面证据和关键页面可采用局部标注加编号说明；必须有实际截图，不伪造竞品画面。没有界面证据时保留带来源的体验比较表。
- 数据库字段分类不等同信息架构；技术时序图不等同产品结构图。跨角色交接优先用业务泳道，技术调用仅在影响交互时展示。
- 开发排期不作为设计分析固定章节，需要时关联独立项目计划。

## 可复用组件契约

固化以下组件的用途、内容结构和验收条件，而非固定模板配额。按当前问题选用；已有组件能回答问题时优先复用。标题说明图表回答的问题，不使用“图一”“功能展示”等空泛命名。

| 组件 | 何时使用／位置 | 最小内容结构 | 关键检查 |
|---|---|---|---|
| 开篇短说明 | 文档开头 | 业务问题、业务目标；必要的一句边界 | 两个短段或引用块即可，不再叠加同义摘要与目标表 |
| Case 说明 | 每个旅程前 | 场景与任务、起点／前提、完成标识 | 遵循 JOB／Case 写法；角色定义共用，不反复复制 |
| 角色旅程白板 | 有阶段协作与交接的 Case | 横向阶段，纵向参与角色；角色行只写动作，连接线承载关键交接物、依赖与结果；下方按需加现状断点、目标体验、设计策略 | 用连接线突出交接；首次交付与异常恢复按触发条件拆分，不编造情绪或岗位 |
| 竞品议题组 | 旅程后、方案前，按研究问题组织 | 我方问题 → 功能体验得分与可信度 → 证据及体验解释 → 我方取舍 → 设计落点 | 评分摘要与单竞品维度明细分表呈现；真实截图可局部编号标注，无截图用带来源简表。证据缺口就地说明，不按厂商堆功能清单 |
| 范围简表 | 整体方案开头 | 用户任务、本期设计覆盖；表后短述非范围 | 不重复旅程，不提前展开待决策，不把设计占位当已批准能力 |
| 对象关系白板 | 多个对象的归属、引用容易混淆时 | 用户可感知对象、关系名称、必要生命周期边界 | 关系线标清归属／引用；不画全量后端数据模型 |
| 入口／页面结构树 | 导航归属或层级需要对齐时 | 现有入口、新增节点、父子层级 | 说明继承与新增；与功能树重复则择一 |
| 页面流程白板 | 跨页面、分支或恢复路径 | 简化页面框、触发操作、成功／失败、取消／返回、系统外边界 | 箭头有动作或条件，失败有去向；与旅程区分业务协作和页面跳转 |
| 页面交互组 | 每个核心页面或高风险载体 | 用户任务 → 完整页面图 → 关键情形／交互与反馈简表 | 图负责布局、表负责规则，不重复逐字段描述；长页拆成清晰子图，不缩成不可读大图 |
| 待决策表 | 方案之后 | 问题、设计影响、当前建议／假设、确认依据与参与角色 | 一个权威位置；不把建议角色写成已指派负责人 |
| 验证清单 | 文档末尾 | Case、任务完成观察、关键高风险情形 | 区分原型走查与真实业务结果；安全等共性检查集中列一次 |

### 框架／拓扑图：分区容器＋对象节点＋带标签连线

需求分析需要解释模块构成、对象归属、资源层级或跨域映射时，默认采用这种图形化方式，不用纯文字列表、代码块或整张静态截图替代。它是对象关系白板的增强形式，不要求额外重复生成一张同义关系图。

- **分区容器**：用有名称的大框区分系统、业务域、资源域或责任边界；仅在真实存在包含关系时嵌套。跨域场景优先左右并列，可比对象按层对齐；单域场景不强行拆成两侧。
- **对象节点**：用尺寸一致的矩形／圆角卡片承载同类对象，名称保持可编辑；按需使用简化设备图标。立体图标不是必需项，缺少原素材时以清楚的节点名称代替，不声称图标内部也能编辑。
- **分组边界**：逻辑集合可用虚线框并标明组名，与实线实体边界区分；必要时提供简短图例，不默认把所有虚线解释成未确认。
- **关系连线**：采用原生直线或折线连接器，明确连接到对应对象／分组／容器，并标注“归属、引用、映射、配对、调用”等实际关系。只有存在方向语义时才用箭头，不能把无方向的配对画成单向数据流。
- **布局层次**：对象与关系分层排布，跨域连线标签放在中间留白区；减少交叉和穿越节点。域、对象、关系保持一致编码，默认清晰蓝绿配色，可随目标文档或用户要求调整。
- **表达边界**：框架图回答“有哪些对象、如何组织和关联”，用户旅程回答“谁如何完成任务”，页面流程回答“从哪里操作、跳到哪里”；三者不相互替代。不为画图扩大需求到完整网络拓扑、底层部署或数据库模型，仅展示帮助理解业务和交互的关系。
- **验证**：核对嵌套、归属、连接端点、方向与标签是否符合需求证据；未知关系标为待确认，不凭示意图推导后台能力。检查原生对象可编辑、正文显示可读、文字无裁切、容器背景不遮挡子节点，并查看飞书实际预览。

固化的是上述构图方法，不是某一张图的服务器数量、产品术语、客户链接或业务关系；用户明确要求时才按原图逐项复刻。

### 页面图的保真度

- 低保真线框图：灰阶为主，表达布局分区、信息优先级、控件类型与关键文案，不进行品牌视觉精修。
- 中保真交互稿：使用接近现有平台的组件形态、真实字段和示例，展示代表性状态、操作与反馈；视觉细节尚非最终定稿。静态图不声称可以操作，交互行为由配套说明补齐。
- 图题明确标记保真度。已具有平台色彩、详细数据与完整控件的页面不笼统称为低保真线框；用户未要求双份时不为同一页面重复生成两种稿件。

### 通用视觉与可编辑性

- 沿用目标文档已有的可读样式；新文档的白板视觉由 `beautiful-feishu-whiteboard` 选择一致风格，不把某个项目的配色或业务对象写成通用要求。
- 同类节点、阶段、角色和状态保持一致的视觉编码，颜色同时有文字含义。主路径突出，辅助证据弱化，避免大面积装饰和不必要连线。
- 白板用原生形状、文本与连接线；表格用原生表格，不把整表截图。页面图和真实竞品截图保留图片形式，维持比例、可读字号与完整边界。
- 以飞书正文实际显示宽度检查文字、重叠、裁切和线条方向。过宽旅程按 Case／子流程拆分，不强行缩小字号。
- 代码块只用于确有必要的调用或配置示例，不代替流程图、旅程或页面图；大量实现代码下沉到 UI spec。

## 写入顺序

1. 读取目标文档并识别标题、已有内容和组件 ID。
2. 空白文档可整体写入；非空文档根据用户范围追加或定点更新。
3. 先创建空白白板并取得 token，再写入经过渲染和检查的节点。
4. 新白板写入成功且实际预览通过后，才删除被其替代的文字列表。
5. 再次读取文档结构，确认标题顺序、组件类型和重复内容。

## 保护规则

- 不用整篇覆盖更新含有白板或人工补充内容的非空文档，除非用户明确要求重建。
- 不把 Markdown Mermaid 代码直接留在飞书正文中。
- 不用静态截图替代用户要求的可编辑流程图；页面线框等真实画面除外。
- 不删除未被新内容成功替代的组件。
- 更新前记录章节与组件标识；定点更新后比对未修改白板、图片是否完整保留。不要假设获取文档返回的白板 token 标签可直接重新插入；按当前工具支持方式原位更新或迁移，并在替代内容验证后移除旧组件。
- 检查实际原生块结构，而非只检查 Markdown 文本。多段内容应形成独立段落；白板预览若为空白占位不能算验证通过，应核查节点及实际文档显示。
