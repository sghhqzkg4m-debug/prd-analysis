# 质量门

## 所有模式

- 读者能理解为什么做、为谁做、做什么、怎么运作、如何验证。
- 开篇仅承载业务问题、业务目标与规划确定的版本定位及来源；规划缺失或冲突时已标待确认，没有自行划分体验优化型／市场竞争型。规划有主次目标时沿用原结论。每个 Case 用一条业务／产品目标融入角色的体验诉求，而非分列两个目标；由此推导设计目标并追踪至验收。没有重复摘要、目标大表或提前展开的待确认清单。范围随方案呈现，待决策后置；局部假设在对应任务、页面或规则处可见。
- 维度按必需、条件必需、可选判断；客户特征、障碍、分期与收益只有在证据和设计影响成立时显示，不留空白占位，也不编造分期或收益。
- 每个 Case 的设计目标都同时回应综合目标中的业务结果与该场景的体验改善；功能、字段或载体仅作为支撑，创建成功与接入成功的完成标识已区分。能够基于可靠基线和一致口径量化时，已填写指标、目标值、测量方式与周期；否则使用可观察标准且未编造数字。
- 目标已通过反向校准：业务／产品目标在同一条表述中说明目标对象的预期业务变化与角色在具体场景中希望获得的体验品质，而非能力清单或两个并列标签；体验诉求不预设手段。设计目标在同一句中包含具体场景、角色、关键设计手段和预期改善，并按任务特点选择前后变化、关键决策或协作交接的表达。手段有需求或设计推断依据，写到机制层，不是空泛形容词、控件／字段清单或“能否判断／完成／修正”的验收清单。前后变化的现状阻碍有证据；具体观察信号在验收中，设计目标能指导设计取舍并回应综合目标；目标正文没有自造 G1/G2 等编号。证据不足处明确标假设，不为追求完整而编造基线或收益。
- 规划包含体验优化目标时，每个受影响 Case 都有证据支持的现状任务路径、关键断点及用户影响，成因与假设已区分，改进机会与优先级有依据，验收能对照现状与目标体验；缺基线时有建立基线或观察任务表现的安排。
- 竞品体验结论有操作或界面证据，架构能力没有被当成易用性验证；旅程中的事实、目标和未知环节明确，关键角色交接可见。
- 事实、决策、推断、待确认和非范围没有混写。
- JOB 写明用户、场景和任务；Case 写明场景和任务，并具备起点／前提、完成标识。连续阶段未被机械写成多个 Case；异常作为分支合并在对应 Case 中，触发、反馈、可执行操作、恢复或退出和完成标识完整，且未另建异常 Case；主路径、分支、失败恢复和返回策略在对应旅程与页面中可追踪。
- 跨角色旅程分别呈现执行角色的动作、关键交接物与结果反馈；首次使用和异常恢复在对应 Case 内按触发条件区分。现状未知项明确，没有虚构岗位、审批或用户情绪。
- 角色表、任务表、旅程和任务闭环图没有重复维护同一过程；范围与页面流程各自回答不同问题，章节编号和交叉引用一致。
- 权限、敏感信息、不可逆操作和异常恢复达到可验收程度。
- 平台输入可选；提供后已经实际参考。
- 已执行竞品分析触发判断；触发时，竞品事实、设计启发与本方案决定可追踪，且未把竞品能力自动转成本期范围；未触发时，HTML 固定章节只说明不展开的原因，不保留空表或占位研究内容。
- 无与交互设计无关的实现过程、工具日志和泛化内容。

## 竞品研究触发时（适用于所有模式）

- 研究问题关联当前设计决定，样本选择有理由；现状替代方案已纳入考虑。研究投入评分、竞品功能体验评分和证据可信度彼此分开。
- 同一任务的起点、前提和完成标准可比；版本、角色、权限等差异没有被误判为体验优劣。
- 关键结论可追踪到观察证据、单项体验得分理由、证据可信度与缺口、适用条件、我方取舍和验证方式；`N/A` 只用于确实不涉及的维度。
- 未核查不等于不支持，截图和能力文档没有被用来证明不可见操作或可用性收益。
- 结论能落实到页面、流程或规则；体验总分没有掩盖关键单项问题，也没有被表述为行业认证、用户实测结果或厂商排名；没有无依据评分、收益数字或范围扩张。
- 飞书正文便于讲解决策，图表按需选择，证据缺口和待验证项没有被附录掩盖。

## analysis-with-wireframe

- 线框覆盖核心页面和高风险载体。
- 画布完整，无裁切、比例变形、文字溢出和交互区域缺失。
- 未确认的入口、组件或后台能力没有被画成既定事实。

## html-delivery

- HTML 可直接在本地浏览器打开，正文、样式、图标、图表和页面草图没有缺失资源或占位内容。
- 使用独立竞品研究详报时，主文与详报的相对链接可双向到达；详报继承主文的视觉语言，窄屏对照内容可读且页面无整体横向溢出；主文保留关键取舍，详报的来源、评分缺口与结论不与主文冲突，两个文件离线打开均完整可读。
- 将 HTML 与实际采用的模板逐项对比：章节 ID、标题与顺序、目录锚点、主要组件及所在章节、CSS 和交互脚本保持一致；不能只继承视觉外观。必要内容在原槽位填充，条件内容的裁剪不破坏固定骨架。
- 页面目录与锚点有效；章节顺序符合设计讲解主线，来源链接靠近相应结论。
- 已在桌面宽度和至少一个较窄视口完成视觉检查；正文无整体横向溢出，文字无裁切，图表可完整阅读，必要时只在图表容器内滚动。
- 用户旅程、信息架构和页面流程没有被简化成缺少连接关系的卡片罗列；不同 Case 的关键路径和失败恢复按实际差异呈现。
- 现状用户旅程符合 [html-current-journey.md](html-current-journey.md)：产品／模块、核心用户、其他目标用户、场景与覆盖范围清楚；横轴由阶段分组与子阶段／动作步骤两级构成，体验维度和参与角色在纵轴；触点与反馈、角色动作、所说所想、现状断点、用户需求、设计点子及衡量证据逐动作列对齐。同一阶段有多个动作时使用稳定动作编号维持纵向追踪；交接、并行、依赖和异常返回由连接线表达，没有用独立的“交接／结果”行替代关系，也没有让连线穿过节点或文字。
- 相邻阶段使用不同但协调的阶段色，子阶段／动作表头继承所属阶段色；阶段交界处另有清楚的竖向边界，未把颜色作为唯一分组手段，也未与痛点、需求或点子的语义色混淆。
- 用户需求由动作和痛点推导，表达期望能力或结果；设计点子与需求分开，标明优先级或待评估状态、对应动作／需求及责任状态，没有把点子写成已承诺范围。
- 旅程图提供所做、所说／所想、情绪曲线、痛点、需求和点子的独立显隐筛选；每个控件只影响当前 Case，切换后动作列仍对齐，不存在无对应内容的空筛选项，也没有修改源数据。
- 模板或结构示例只使用方括号提示语，不填入具体业务案例；生成真实项目 HTML 时已用证据内容替换提示语，并删除不适用的可选行。没有研究或测量证据时，不生成情绪曲线、耗时或满意度分值。
- 进入页面方案时已展示关键页面草图；草图与流程、状态、权限和验收结论一致。
- 用户提供模板或品牌规范时，Logo 比例、字体、色彩和核心组件语言已继承；内容没有为了套模板而遗漏必要分析。
- 同一主题更新原 HTML，没有生成 `v2`、`final2` 等无意义副本。
- 最终回复提供可点击的 HTML 文件链接；未提供或未同步飞书时，没有声称飞书已更新。

## feishu-delivery

- 先读后写，写入范围与用户要求一致。
- 文档主体服务设计评审：用户、任务、流程、页面、状态、权限、反馈和恢复是主线；技术实现细节没有挤占正文。
- 直接影响交互的技术约束已保留为简短约束或待确认项；后端选型、算法实现、协议矩阵和性能实现已下沉。
- 流程、层级和对象关系使用合适的原生组件。
- 框架／拓扑图采用分区容器、对象节点与带标签的原生连接线；归属、分组、映射与调用语义清楚，配对未被误画为单向流。没有用文字清单替代关系可视化，也未混淆框架图与旅程／页面流程或扩展无关技术细节。
- 已按组件契约选择最小充分组合，没有为了凑模板生成所有图表；旅程、页面流程、对象关系各自回答不同问题。页面图已准确标注低保真／中保真，静态图不声称可操作。
- 白板可编辑，经过本地渲染、结构检查和飞书实际预览。
- 图片宽高比正确；旧内容只在新内容成功后删除。
- 回读文档确认章节顺序、组件 token、重复和遗漏。
- 检查粘贴后的原生表格是否有实际内容、说明列是否可读；替代块验证后清理遗留空表或重复块。

- UI 规格与飞书设计结论一致，不增加新业务决定。
- 页面契约、组件语义、状态、权限、Mock、实现边界和验收完整。
- 精确组件名、Props、API 和文件位置有 Workspace 证据，或明确要求实现阶段核查。
- 未确认项在生成规格中有安全的默认处理，不被静默决定。
