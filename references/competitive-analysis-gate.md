# 竞品分析触发与功能体验评价

竞品分析不是固定章节。先判断它是否会改变当前设计决策，再决定投入深度。完整性指“研究问题 → 体验证据 → 功能体验评分与可信度 → 差异原因 → 设计取舍 → 验证”的闭环，而非报告篇幅。

## 1. 研究投入评分

针对功能或关键决策评分，不以整个产品的高分带动所有通用控件研究。每项按 `0–2` 分计分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 功能重要度 | 辅助展示 | 支撑任务 | 核心任务或核心能力 |
| 决策可逆性 | 随时可改 | 有迁移成本 | 对象、入口或数据一旦上线很难改 |
| 行业成熟度 | 无稳定范式 | 有零散做法 | 已形成成熟产品模式 |
| 需求不确定性 | 路径清晰 | 局部未知 | 方案、边界或用户心智不清晰 |
| 差异化风险 | 无关差异化 | 需避免落后 | 需要明确采用、拒绝或超越的模式 |

按总分选择研究等级：

- `0–3`：跳过。直接基于用户证据和平台约束设计，不创建空洞的竞品章节。
- `4–6`：快速扫描。比较 `2–3` 个最相关替代方案，只输出会影响设计的结论。
- `7–10`：聚焦分析。比较 `3–5` 个直接竞品、相邻成熟产品或现状替代方案，形成可追踪决策。

评分是投入参考，不是客观体验分数。用户明确要求分析时按其范围执行；权限、凭证、不可逆操作等高风险未知项可以提高研究深度。样本数量为参考，不是完成指标。已有证据足以支持当前决策时停止扩展；资料不足时缩小结论并记录缺口，不凑厂商或虚构验证。

## 2. 研究集合

不要把“竞品”等同于同赛道厂商。候选集合至少考虑：

1. 直接竞品：解决相同客户 Job 的产品。
2. 相邻成熟模式：对象模型或交互机制高度相似的产品。
3. 现状替代方案：人工操作、自建工具、表格、脚本或放弃该任务。

选择样本时优先覆盖不同策略，不按厂商数量凑表格。

每个入选参照说明选择理由、参考机制与适用边界；跨行业模式不能默认整套移植。先统一用户任务的起点、前置条件和业务完成标准，再比较不同方案。版本、部署形态、套餐、专业程度、角色与权限造成的差异需注明，不可比部分不强行排名。

## 3. 只研究能改变设计的问题

搜索前明确待决策问题、使用者、触发场景、业务完成标识、关键约束与研究范围。报告开头说明每个关键研究问题从哪项需求输入、Case 断点、高风险未知项或设计决策产生，以及回答它会影响什么；不要从竞品功能清单倒推研究问题。聚焦分析考虑以下八部分；快速扫描可合并表达，但仍需保留问题—证据—取舍—验证链条：

| 部分 | 应回答的问题 |
|---|---|
| 分析目标 | 哪些设计疑问尚未解决，会影响哪些决策？ |
| 用户与业务情境 | 谁在什么情境下完成什么，受到什么限制？ |
| 参照选择 | 为什么选择这些产品、跨行业模式或现状替代方案？ |
| 端到端任务体验 | 发现入口、准备、操作、交付、验证和后续维护哪里存在断点？ |
| 关键交互机制 | 信息、配置、反馈和恢复如何帮助或阻碍任务？ |
| 横向比较与原因 | 各方案的收益、代价与适用条件是什么？ |
| 我方设计取舍 | 借鉴、改造、不采用或延后什么，落实到哪里？ |
| 验证与证据边界 | 哪些已观察、哪些是推断，下一步如何验证？ |

研究问题应限定在以下范围：

- 用户把什么当作核心对象，如何命名和识别？
- 功能入口放在哪里，如何与上游、下游对象衔接？
- 主任务分几步，哪些信息需要渐进披露？
- 哪些配置应暴露给用户，哪些应由系统托管？
- 状态如何表达，失败后如何诊断和恢复？
- 权限、凭证、租户和敏感信息边界如何可见？

同时按任务需要考察：配置者与使用者的角色交接、结果确认、持续维护、一致性与可访问性。若信息不能影响当前设计决策，不写入设计正文。

研究观察可按问题覆盖以下内容，不机械填满；正式评分统一使用第 5 节的八维口径：

| 维度 | 重点观察 |
|---|---|
| 入口与可发现性 | 命名、归属和上下游衔接是否符合预期 |
| 概念与信息理解 | 对象关系、术语和信息优先级 |
| 任务组织与效率 | 操作顺序、重复输入、复用与批量处理 |
| 决策与配置负担 | 专业判断、默认值、推荐与渐进披露 |
| 反馈与结果确认 | 进度、结果、下一步；提交成功与业务完成的区别 |
| 异常与恢复 | 原因、影响、保留进度、修正、重试与回退 |
| 安全与控制感 | 权限、敏感信息、危险操作、影响范围与撤销 |
| 多角色协作 | 配置、使用、审批和维护之间的信息与责任交接 |
| 一致性与可访问性 | 同类操作一致性、非纯颜色状态表达、键盘访问等 |
| 持续使用与维护 | 首次配置后的查看、修改、扩展、停用和排障 |

一致性与可访问性作为横切检查，不单独计权；发现严重问题时影响对应的理解、效率、控制或有效性得分，并单列风险说明。

步骤少不等于体验好，配置多不等于能力强。比较是否帮助用户正确决策并完成业务任务，而非仅比较点击数或视觉精美程度。竞品内部动机、技术限制与设计原因无证据时只能作为解释假设。

## 4. 证据规则

- 会变化的产品能力必须查当前官方文档或其他一手资料，并保留链接和核查日期。
- 用户提供的竞品截图只能证明截图中可见的模式，不能证明完整能力，也不能直接转化为本期需求。
- 明确区分“竞品事实”“设计启发”“本方案决定”。
- 竞品有某能力不构成采用理由；必须说明是否采用、拒绝或延后，以及原因。
- 不以功能数量排名代替用户任务和差异化判断。
- 实测需记录任务、角色及关键条件；版本和套餐可知时记录，不可知时注明。未找到不等于不支持，无法验证写“未核查”。
- 静态截图不能证明点击后的反馈、异常恢复和完整流程；不得自制竞品界面冒充证据。
- 分析具体竞品功能内容时，优先配实际产品界面截图或连续操作录屏，让读者看到任务起点、对象、关键操作与反馈。如果能访问相关功能的真实产品页面，尽量保存并提供完整页面原图，保留页面标题、导航、对象上下文、主要操作区和结果状态；跨页面任务按关键步骤分别保存完整页面，必要时配连续录屏。正文可用局部放大图解释细节，但必须能打开对应完整页面，不用裁切片段代替整体证据。每张图标注产品／版本或访问条件（可知时）、角色与触发条件、来源链接和截取日期，并用简短标注区分“图中可见事实”“体验推断”“对我方的启发”。截图只支持其可见范围；官网产品介绍页、架构示意图、宣传图或文档摘录须明确标为相应资料类型，不能冒充真实控制台界面或完整任务证据。只有公开介绍页时，可提供该页的完整链接或全页留档供查证，同时明确真实功能页面仍未取得。无法取得可核查截图时，保留证据缺口，不生成仿真截图补位。
- 不编造耗时、成功率、满意度或情绪曲线。功能体验评分必须遵循第 5 节统一口径并标注证据可信度；量化比较需要一致任务与测量方法，启发式评价注明其非用户实测性质。
- 资料冲突时记录时间和条件差异，暂缓依赖该事实的结论，不静默选择有利证据。

## 5. 竞品功能用户体验评分

研究投入评分回答“是否需要研究、研究多深”；本节回答“参考竞品的这个功能，用户体验表现如何”。评分对象是同一用户任务下的具体功能或 Case，不给整个厂商或整款产品笼统打分。开始评分前统一用户角色、任务起点、前置条件和业务完成标准；不可比部分标 `N/A` 或单独说明，不强行进入总分。

默认使用以下八个维度。每项 `1–5` 分；当前功能确实不涉及的维度标 `N/A`，将其权重按剩余维度比例重新归一化。维度存在但证据不足时标“未核查”，不得用 `N/A` 隐藏证据缺口。

| 维度 | 默认权重 | 重点观察 |
|---|---:|---|
| 任务有效性 | 20% | 用户能否正确完成任务并获得真实业务结果 |
| 信息理解与决策负担 | 15% | 对象、术语、配置影响和信息层级是否易理解，是否要求不必要的专业判断 |
| 反馈与结果确认 | 15% | 操作反馈、执行进度、当前状态、下一步和真实完成是否清楚 |
| 异常预防与恢复 | 15% | 是否预防错误、定位原因、保留进度，并支持修正、重试、回退或退出 |
| 操作效率 | 10% | 是否存在无效步骤、重复输入、频繁切换、等待和无法复用 |
| 可发现性与易学性 | 10% | 入口、功能能力和下一步是否容易找到、理解和掌握 |
| 安全与用户控制 | 10% | 权限、敏感信息、影响范围、确认、取消、撤销和中断是否可控 |
| 协作与持续维护 | 5% | 结果能否交接，后续查看、修改、扩展、停用和排障是否顺畅 |

评分锚点：

| 分数 | 统一判断 |
|---:|---|
| 5 | 表现优秀，完整支持任务推进，未发现影响当前任务的明显问题 |
| 4 | 表现良好，有少量摩擦，但不明显影响任务完成和结果判断 |
| 3 | 基本可用，可以完成任务，但存在明显理解、操作或恢复成本 |
| 2 | 体验较弱，多处阻碍任务，容易造成错误、返工或不确定性 |
| 1 | 严重影响任务完成，或存在明显安全、恢复和结果判断风险 |

每个单项分数必须附观察事实和影响解释，不允许先给印象分再补理由。总分按 `Σ（单项得分 ÷ 5 × 归一化后的权重）` 计算为百分制，仅用于辅助定位整体表现：`85–100` 优秀，`70–84` 良好，`55–69` 基本可用但有明显短板，`40–54` 较弱，`20–39` 高风险。该区间是本 Skill 的内部分析口径，不表述为行业认证、真实用户满意度或市场排名。

总分不能替代单项判断。输出时至少指出最高与最低体验维度、造成差异的交互机制、适用条件，以及我方准备借鉴、改造、规避或继续验证的内容。若研究问题只涉及少数体验维度，可只评分这些维度并明确范围，不为生成总分补评无关维度。

### 证据可信度

功能体验总分旁单独标注可信度，不与体验分相加：

| 等级 | 证据条件 | 可支持的判断 |
|---|---|---|
| A 高 | 完整实际操作或用户测试；版本、角色、权限和任务条件清楚 | 可评价已覆盖任务的完整流程及相应体验维度 |
| B 中 | 官方连续演示、连续截图或完整操作说明，任务条件基本清楚 | 可评价被连续证据覆盖的流程，不声称真实成功率或满意度 |
| C 低 | 静态截图、局部页面或产品文档 | 只评价可见的信息呈现和局部机制 |
| D 待核查 | 宣传材料、第三方转述，或证据无法支持当前体验判断 | 不形成确定性体验分；记录待核查项 |

静态截图不能支持点击反馈、耗时、任务成功、异常恢复或持续维护评分。没有用户测试时，不把专家启发式评分写成真实用户表现；没有统一任务和测量方法时，不编造耗时、成功率、满意度或改善百分比。只有全部适用维度均有足够证据时才输出完整总分；资料只覆盖部分流程时，输出“局部体验评分＋可信度”，列出未覆盖环节，不把局部得分包装为完整功能总分。

为避免飞书超宽表格，使用一张摘要表和按竞品拆分的明细表：

| 竞品功能 / Case | 总分 / 等级或局部评分 | 最高与最低维度 | 可信度 | 主要缺口 |
|---|---|---|---|---|

| 体验维度 | 权重 | 得分 | 观察事实与影响解释 | 证据 / 缺口 |
|---|---:|---:|---|---|

## 6. 输出格式

优先围绕相同用户任务进行体验比较，而非按厂商能力逐项盘点。考察首次理解、准备与配置、交付接入、异常判断、变更恢复中的认知负担、决策数量、反馈时机和交接成本。

当读者需要先理解每个参照产品时，可先用简短的“产品定位 → 与本题有关的功能内容 → 关键截图／证据 → 观察点”建立上下文，再归纳跨产品洞察。洞察可按功能、交互、可视化分组，也可按任务阶段分组，选择最能解释当前设计问题的一种；每条仍需写清观察事实、对用户任务的可能影响、设计启发及证据边界。功能清单不应替代横向任务比较；缺少真实界面证据时，可视化体验写“未核查”，不从官网示意图推断页面质量。

证据优先级：实际操作记录、官方界面或演示、官方操作教程。架构/API 文档只能证明能力与对象关系，不能证明页面易用、操作步骤、默认值或用户满意度。没有体验证据时写“能力参考，交互待核查”。区分观察事实、体验推断和设计建议；不能将启发称为已验证的可用性结论。

每条关键结论包含：观察事实及来源 → 功能体验维度与得分理由 → 证据可信度和缺口 → 体验收益／负担 → 适用条件 → 我方取舍 → 验证方式。比较未覆盖的环节明确标缺口，不补写推测的竞品界面。

建议使用紧凑表格，避免飞书超宽表格；少量结论可用短段落：

| 用户任务 / 问题 | 参照做法及证据 | 体验收益与负担 | 适用条件 / 缺口 |
|---|---|---|---|

| 竞品功能 / Case | 体验总分与高低分维度 | 证据可信度 / 缺口 | 对我方的参考结论 |
|---|---|---|---|

| 设计问题 | 借鉴 / 改造 / 不采用 / 延后及理由 | 对应页面或规则 | 验证方式 |
|---|---|---|---|

理由必须联系本项目用户与约束；“竞品都有”“大厂如此”“页面清晰”不是充分理由。重要结论以简短标识关联证据和设计，不重复粘贴资料。验证写清任务、观察点和通过依据；没有基线不虚构改善百分比。

随后收敛为四类结论：

- 竞品证据支持继续保留的设计决定（不等于本产品可用性已验证）。
- 因竞品证据而调整的设计决定。
- 明确不进入本期范围的能力。
- 尚待用户走查或真实任务验证的假设。

## 7. 飞书写入边界

本节的正文／附件分层也适用于 HTML：主 HTML 只保留能支持当前设计评审的关键比较与结论；用户要求深入阅读或证据量较大时，在同一交付目录提供可从主文下钻的独立自包含 HTML 详报，并设置返回主文的链接。详报展开完整研究记录，但沿用同一组研究问题、证据编号和设计结论，不复制出第二套业务决定。尚未取得同任务体验证据时，详报应标明“阶段性研究记录”，保留评分缺口，不因页面名称为“详报”而补造完整体验评分。

详报按读者的推理顺序组织：先交代选题依据和同任务口径，再逐题给出参照产品的选择理由、相关功能、关键截图或操作证据、可得判断及缺口、我方取舍和下一步验证，最后保留横向比较、评分缺口与来源。有多个关键研究问题时，优先让每个问题独立形成这一连续单元，并在目录或概览中一一对应。关键产品证据和截图直接放在它所回答的问题旁；同一产品用于不同问题时，只写该问题相关的机制与证据边界。完整产品档案和横向矩阵仅在确有额外查证价值时作为补充，不另开重复的“产品与证据”章节让读者跨章拼接答案。若相邻章节重复取舍与验证、评分缺口与来源，可合并为一个阅读单元，以小标题保留追溯入口；不为固定章数而拆分同一论点。

- 默认按设计问题或用户任务组织，不逐厂商堆产品介绍。研究支持或改变关键决策时才增加对应章节；用户明确要求完整报告时按其范围展开，并如实披露未覆盖环节。
- 面向读者的标题、卡片、图注和表格优先使用“研究问题名称、产品名称、设计取舍名称”，不要让 Q1／E2／D3 等内部编号承担主要指代。页内跳转、文件名和内部追溯键可以保持稳定，但正文应在第一次出现时就说清对象；确需编号时，将名称同处展示，避免先见序号后找定义。
- 正文只保留与对象、入口、流程、状态、安全或恢复相关的结论；原始功能盘点和长篇资料下沉到研究附件。
- 竞品分析不得自动扩大 MVP 范围。没有新增范围时明确写“本次分析未新增功能范围”。
- 正文保留研究问题与结论摘要、关键任务比较、必要的截图标注、我方取舍和待验证项；完整记录、更多截图和来源下沉附录。关键证据缺口不能只藏在附录。
- 截图围绕关键设计问题选取，标注触发条件、可见操作与反馈，并紧邻相关证据、推断和取舍呈现；避免把大量图片集中成与结论脱节的图库。跨阶段或角色断点用任务旅程对照，步骤与分支差异用并列流程图，入口归属用结构图，异常用状态与恢复路径表。按关系选图，不为形式完整强制全部生成。
- 不默认加入市场份额、商业模式、研发排期和全量能力盘点；新增功能建议明确标待决策，不混入已确认范围。
